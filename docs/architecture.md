# Architecture

RUET Chottor is a TypeScript monorepo with three workspaces:

```
apps/web         Next.js app the students use (browser)
apps/api         NestJS API: REST under /api/v1, Socket.IO for real time
packages/shared  Zod schemas, types and constants used by both
```

```
 Browser ──HTTP (cookies)──▶ apps/api ──▶ PostgreSQL (Neon, via Prisma)
    │                          │
    └────── Socket.IO ─────────┘──────▶ Redis (Upstash): cache, rate limits, OTPs, socket adapter
```

## Why this shape

- **One language everywhere.** Contributors only need TypeScript.
- **Shared schemas.** A request body is defined once with Zod in `packages/shared`. The web form and the API both
  validate against the same schema, so they can never disagree.
- **Separate API.** The API serves the web app now and could serve a mobile app later.
- **Modules, not layers.** Every feature (chat, news, bus, ...) lives in its own folder in each workspace and can be
  switched off with a feature flag. See CLAUDE.md §4 for the rules.

## API (`apps/api`)

| Path | Purpose |
|---|---|
| `src/main.ts` | Starts the server |
| `src/app.setup.ts` | HTTP setup shared with tests: `/api/v1` prefix, helmet, cookies, CORS, origin check, error filter |
| `src/app.module.ts` | Registers the core and each enabled feature module |
| `src/core/config` | Validates environment variables at startup (Zod) |
| `src/core/http` | Error filter (`{ error: { code, message } }`), `ZodValidationPipe`, CSRF origin check |
| `src/core/auth` | Global `AuthGuard` (every route private unless `@Public()`), `@Roles`, `@CurrentUser`, session cookies, access-token store |
| `src/core/rate-limit` | `RateLimitService`: fixed-window counters in Redis |
| `src/core/mail` | `MailService`: SMTP, or an Ethereal test inbox in development (ADR 0004) |
| `src/core/prisma` | `PrismaService`: the only way to reach the database |
| `src/core/redis` | `RedisService`: shared Redis connection |
| `src/core/meta` | `GET /health` and `GET /features` |
| `src/core/realtime` | Socket.IO adapter (origin check) and cookie login for sockets (ADR 0008) |
| `src/modules/<module>` | Feature modules, e.g. `auth`, `users`; real-time ones add a `*.gateway.ts` |
| `prisma/` | Schema, migrations, seed scripts |

The API is an ES module project (`"type": "module"`), so relative imports end in `.js`.
Prisma 7 generates its client into `src/generated/prisma` (git-ignored); it is regenerated by `build`, `typecheck` and `test`.

## Web (`apps/web`)

| Path | Purpose |
|---|---|
| `src/app/` | Routes only. Pages stay thin and render feature components |
| `src/features/<module>/` | Components, hooks, API calls and `help.ts` (guidance text) per module |
| `src/components/ui/` | shadcn/ui primitives (Radix based) |
| `src/components/guide/` | `PageHeader`, `InfoTip`, `FirstVisitGuide` — the self-explaining UI (CLAUDE.md §8). Closed guides are cached in localStorage; `GuideSyncContext` lets the `users` feature also store them on the server for logged-in members |
| `src/components/layout/` | Header and footer |
| `src/components/form/` | `FormField` (label + info tip + error) and `FormError` |
| `src/lib/` | API client, Socket.IO client (`socket.ts`), feature flags hook, utilities |
| `src/styles/theme.css` | The only place colors are defined |

Client data is fetched with TanStack Query through `apiRequest()`, which always sends cookies and validates
responses with the shared schemas.

## Sessions

Login is two steps (password, then an emailed code). The API then sets two `httpOnly` cookies: a 15-minute access
token and a 30-day refresh token that rotates on every use. Both are random strings looked up server-side, not JWTs
(ADR 0005). `apiRequest()` in the web app refreshes the session once and retries when the API answers
`SESSION_EXPIRED`. See [modules/auth.md](modules/auth.md).

## Real time

Socket.IO runs on the API's HTTP server, one namespace per module (`/chat` so far). A socket logs in with the same
session cookie as HTTP and joins only its own `user:<id>` room. Services save to Postgres first and then push the
event to each recipient's room, so the socket is a delivery channel and HTTP stays the source of truth: after a
reconnect the browser fetches what it missed. See [ADR 0008](decisions/0008-realtime-socket-io.md) and
[modules/chat.md](modules/chat.md).

## Feature flags

`FEATURE_<MODULE>=true` in `apps/api/.env` switches a module on. The API exposes the list at `GET /api/v1/features`;
the web app builds its navigation from it, so the API is the single source of truth.
In the API, `ConditionalModule.registerWhen` in `app.module.ts` skips disabled modules, so their routes do not exist.

Modules talk to each other only through exported services. Example: `directory` imports `UsersModule` and calls
`UsersService.listPublic()`, so the rules for *what* a member may see about another member (privacy, hiding
suspended accounts) live in one place, `users`. Likewise `admin` uses auth's exported `SessionsService` to log a
suspended member out, and exports `ModerationLogService` so every module records staff actions in the same
append-only log ([ADR 0007](decisions/0007-moderation-log-and-account-sanctions.md)).
