# Architecture

RUET Chottor is a TypeScript monorepo with three workspaces:

```
apps/web         Next.js app the students use (browser)
apps/api         NestJS API: REST under /api/v1, Socket.IO for real time
packages/shared  Zod schemas, types and constants used by both
```

```
 Browser ──HTTP (cookies)──▶ apps/api ──▶ PostgreSQL (Neon, via Prisma)
    │                          │
    └────── Socket.IO ─────────┘──────▶ Redis (Upstash): cache, rate limits, OTPs, socket adapter
```

## Why this shape

- **One language everywhere.** Contributors only need TypeScript.
- **Shared schemas.** A request body is defined once with Zod in `packages/shared`. The web form and the API both
  validate against the same schema, so they can never disagree.
- **Separate API.** The API serves the web app now and could serve a mobile app later.
- **Modules, not layers.** Every feature (chat, news, bus, ...) lives in its own folder in each workspace and can be
  switched off with a feature flag. See CLAUDE.md §4 for the rules.

## API (`apps/api`)

| Path | Purpose |
|---|---|
| `src/main.ts` | Starts the server |
| `src/app.setup.ts` | HTTP setup shared with tests: `/api/v1` prefix, helmet, cookies, CORS, error filter |
| `src/app.module.ts` | Registers the core and each enabled feature module |
| `src/core/config` | Validates environment variables at startup (Zod) |
| `src/core/http` | Turns every error into `{ error: { code, message } }` |
| `src/core/prisma` | `PrismaService`: the only way to reach the database |
| `src/core/redis` | `RedisService`: shared Redis connection |
| `src/core/meta` | `GET /health` and `GET /features` |
| `src/modules/<module>` | Feature modules (from Phase 1) |
| `prisma/` | Schema, migrations, seed scripts |

The API is an ES module project (`"type": "module"`), so relative imports end in `.js`.
Prisma 7 generates its client into `src/generated/prisma` (git-ignored); it is regenerated by `build`, `typecheck` and `test`.

## Web (`apps/web`)

| Path | Purpose |
|---|---|
| `src/app/` | Routes only. Pages stay thin and render feature components |
| `src/features/<module>/` | Components, hooks, API calls and `help.ts` (guidance text) per module |
| `src/components/ui/` | shadcn/ui primitives (Radix based) |
| `src/components/guide/` | `PageHeader`, `InfoTip`, `FirstVisitGuide` — the self-explaining UI (CLAUDE.md §8) |
| `src/components/layout/` | Header and footer |
| `src/lib/` | API client, feature flags hook, utilities |
| `src/styles/theme.css` | The only place colors are defined |

Client data is fetched with TanStack Query through `apiRequest()`, which always sends cookies and validates
responses with the shared schemas.

## Feature flags

`FEATURE_<MODULE>=true` in `apps/api/.env` switches a module on. The API exposes the list at `GET /api/v1/features`;
the web app builds its navigation from it, so the API is the single source of truth.
